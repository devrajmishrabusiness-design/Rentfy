# Rentfy Operations Guide

## Health Endpoint

**GET /api/health**

Returns JSON indicating whether the application is healthy.

### Response shape
```json
{
  "ok": true,
  "status": "healthy",
  "timestamp": "2026-07-21T12:00:00.000Z",
  "version": "0.1.0",
  "environment": "production",
  "checks": {
    "env_supabase_url": "ok",
    "env_supabase_anon_key": "ok",
    "supabase_connectivity": "ok"
  },
  "metrics": {
    "property.created": 12,
    "lead.created": 5,
    ...
  }
}
```

### Status codes
- `200` — healthy (all checks pass)
- `503` — degraded (one or more checks fail)

### Checks performed
1. `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are present
2. Supabase connectivity: a lightweight `SELECT id FROM properties LIMIT 1` via the anon client

### Usage
Point your uptime monitor (Vercel, UptimeRobot, Datadog, etc.) at `https://<domain>/api/health`. A 200 response means the server is running and can talk to Supabase.

### What it does NOT expose
- Service-role keys
- Database contents
- Authenticated user data
- Storage bucket details

## Request IDs

Every API request receives a unique `X-Request-Id` header, generated by the proxy (`proxy.ts`) using `crypto.randomUUID()`.

### Flow
1. The proxy intercepts the request and generates a UUID.
2. The UUID is injected into the response headers (`X-Request-Id`).
3. Each API route handler reads the request ID from the incoming headers via `REQUEST_ID_HEADER` (exported by `lib/observability.ts`).
4. A request-scoped logger (`rlog`) is created from the module-level logger using `createRequestLogger()`. Every log entry from `rlog` carries the request ID, route, HTTP method, and authenticated user/agency/renter IDs (if available).

### Correlation
Search all logs (Vercel Logs, stdout, etc.) for the `requestId` field to trace a single request across multiple log entries, error messages, and connection spans.

## Structured Logging

The application uses `@rentfy/engine-sdk`'s `DefaultStructuredLogger` with `ConsoleLogTransport` (JSON stdout).

### Logger hierarchy
- **Module-level logger**: one per API route file, configured with `source: "api/<name>"`.
- **Request-scoped logger (`rlog`)**: created per-request via `createRequestLogger()` — a child of the module-level logger with request context bound as base metadata.

### Log entry fields
Every log entry carries:
- `timestamp` — ISO timestamp
- `level` — `trace`, `debug`, `info`, `warn`, `error`, `fatal`
- `message` — human-readable description
- `source` — route name (e.g. `api/visits`)
- `requestId` — proxy-generated correlation ID (only on request-scoped loggers)
- `route` — API path (e.g. `/api/visits`)
- `method` — HTTP method
- `userId`, `agencyId`, `renterId` — when authenticated
- `context` — additional metadata (error details, property IDs, etc.)

### What is NEVER logged
- Passwords
- Tokens (JWT, service-role keys)
- Cookies (session, auth)
- OTP codes
- User-supplied PII beyond IDs

## Error Reporting

`lib/error-reporter.ts` provides a centralized `ErrorReporter` interface with a `DefaultErrorReporter` implementation that logs to the structured logger.

### Future Sentry integration
1. Create a `SentryErrorReporter` implementing the `ErrorReporter` interface.
2. Call `setErrorReporter(new SentryErrorReporter(...))` once at server startup.
3. All existing `report()` and `warn()` call sites will automatically flow to Sentry — no code changes needed in route handlers or server actions.

### Using the reporter today
```ts
import { getErrorReporter } from "@/lib/error-reporter";

const reporter = getErrorReporter(logger);
reporter.report(new Error("..."), { route: "/api/visits", userId: "..." });
```

## Metrics

`lib/metrics.ts` provides lightweight in-memory counters. No external infrastructure required.

### Tracked metrics
| Counter | When incremented |
|---|---|
| `auth.success` | User authenticated successfully |
| `auth.failure` | Authentication failed |
| `property.created` | New property created |
| `property.updated` | Property updated |
| `property.deleted` | Property deleted |
| `lead.created` | New lead created |
| `lead.updated` | Lead status updated |
| `visit.created` | New visit scheduled |
| `visit.updated` | Visit status changed |
| `rate_limit.blocked` | Rate limit rejected a request |
| `api.error` | API returned a 500 |
| `api.warning` | API returned a 4xx |
| `admin.action` | Admin performed an action |

### Usage
```ts
import { increment, readAll } from "@/lib/metrics";

increment("auth.success");
// metrics are exposed via GET /api/health
```

### Future
Swap counters for OpenTelemetry or Prometheus when monitoring infrastructure is added.

## Monitoring Future State

When a production issue occurs, you can answer:

1. **What happened?** — Search logs for the `requestId` from the error page or client console.
2. **Who was affected?** — The `userId` or `agencyId` is logged with every request-scoped entry.
3. **Which request failed?** — The `requestId` ties the entire request span together.
4. **Why did it fail?** — Error messages and stack traces are logged with `rlog.error(...)`.
5. **How often?** — Check `/api/health` for metric counters or aggregate log queries.
